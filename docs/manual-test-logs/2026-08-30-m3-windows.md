### Finding P-1 — the documented emergency exit is not sufficient (matrix defect)

`docs/manual-tests.md` Setup says to keep a terminal open with
`taskkill /IM keygnosys-core.exe /F` ready. **That exit cannot be used under the
conditions it exists for.** While the layer is latched, `layer_engine.cpp:302-305`
swallows every unbound non-modifier key, so no letter reaches any window — the
command cannot be typed. `Ctrl+C` is equally unavailable: `Ctrl` is forwarded as a
modifier (`:297-300`) but `KeyC` is swallowed.

Severity: the matrix's stated safety mechanism is inert in the latched state.
Proposed fix: replace it with E1/E2 above.

### Finding P-2 — the Setup block crashes on this machine (matrix defect)

The Setup block runs the binary with no PATH prefix:

```sh
cmake --preset default && cmake --build --preset default
./build/default/core/keygnosys-core.exe
```

Followed literally in MSYS2 bash, this segfaults **12/12** before printing its
banner. Cause is DLL resolution, not a product defect: the binary is UCRT64-linked
(imports `api-ms-win-crt-*`) but `/mingw64/bin` precedes `/c/msys64/ucrt64/bin` on
this PATH, so it loads MINGW64's msvcrt-based `libstdc++-6` / `libgcc_s_seh-1` /
`libwinpthread-1`. The `debug` build survives the mismatch; the optimized build
does not.

| Launcher | debug | default (RelWithDebInfo) |
|---|---|---|
| MSYS2 bash, no PATH prefix | 5/5 OK | **5/5 SEGV** |
| MSYS2 bash, `PATH=/c/msys64/ucrt64/bin:$PATH` | — | 5/5 OK |
| Native Windows launch | 5/5 OK | 5/5 OK |

The repo's own verification commands already carry the `PATH=` prefix; only the
manual-test Setup block omits it. Proposed fix: add the prefix there too.

### Boundary

Everything up to and including the hook thread's control handling is healthy.
`onHook` itself never produces a `PhysicalRecord`. Since `publishPhysical` is
called on every path that gets past the two early returns, either the callback is
never invoked, or it returns at the `LLKHF_INJECTED` / `!key.valid()` guards
(`hook_input.cpp`). The keymap is ruled out: `test_scancode_keymap` round-trips
100+ codes and the control experiment's first event was scancode `0x1F`, which the
table maps to `KeyS`.

### RESOLVED 2026-09-01 — H1 confirmed

Temporary uncommitted instrumentation added counters to `HookInput` and changed
exactly one behaviour: `waitTimeout()` returning `50` instead of `INFINITE` at
idle. No other change. Counters are atomics; nothing was logged, allocated or
blocked inside the callback, and reporting happens from the hook thread's loop
outside the callback.

Human-confirmed window: operator was asked to type continuously for 10 s and
replied "done".

| Counter | Before window | After window | Delta |
|---|---|---|---|
| Independent-hook callbacks | — | **529** | 529 (first `vk=0x20 scan=0x39 flags=0x00`) |
| `trampoline` | 115 | 1931 | **+1816** |
| `hcAction` | 115 | 1931 | **+1816** |
| `injected` (skipped by design) | 9 | 328 | +319 |
| `validKey` translated | 106 | 1589 | **+1483** |
| `invalidKey` | 0 | 14 | +14 |
| `PhysicalRecord` attempted | 106 | 1589 | **+1483** |
| `PhysicalRecord` enqueued | 106 | 1589 | **+1483** |
| `hookLosses` | 0 | 0 | 0 |

Install facts: `hhook=0x5b251bd1`, `module=0x7ff6ee320000` (the exe's own base),
`GetLastError=0`, `installAttempts=1`, `installOk=1`, pid `31036`, hook thread
`34416`.

**Conclusion: H1.** The single change of capping the idle wait made callbacks
appear. Installation was never the problem — the same arguments, module handle
and thread produced zero callbacks with `INFINITE` and 1816 with `50 ms`.
`recAttempt == recEnq` exactly, so the publication ring never dropped anything;
`invalidKey=14` out of 1589 is ordinary unmapped-key traffic, not a translation
failure. H2 is excluded.

### Original hypothesis (now confirmed)

`waitTimeout()` returns `INFINITE` whenever no grace deadline is pending, which is
the steady state. The thread then blocks in `MsgWaitForMultipleObjectsEx` and
never reaches the `PeekMessageW` on the next line — which the comment at `:261`
identifies as what actually dispatches the hook. The comment at `:255-256` asserts
"`QS_ALLINPUT` is what lets the system call the hook while we are here"; that
assumption is what needs testing.

Evidence 8 complicates this: the thread demonstrably does reach `PeekMessageW`
whenever a control arrives. A poke test (399 control messages at 20 Hz, forcing
~400 `PeekMessageW` calls) produced no key events either — but it is **not known
whether keys were pressed during that window**, so that run is inconclusive, not a
refutation.

The design note's §4 chose this single-primitive wait deliberately ("One
primitive does both jobs"). If the hypothesis holds, that choice is the defect.

### Not a confound

Windhawk (`windhawk.dll`, Engine 1.7.3) is injected into the core process
(thread 2, `WindhawkMainLoopThreadAttachExempt`). It was considered and
**excluded**: the control experiment's own hook, running under the same Windhawk,
received all 94 callbacks.

# 2026-09-02 — permanent fix verified live

## What the repair was

`GetMessageW` replaces `MsgWaitForMultipleObjectsEx` as the hook thread's
blocking primitive. Control wakeups became coalesced `PostThreadMessageW`
doorbells over the same SPSC ring; the grace deadline became a one-shot
`SetTimer`. See `kgn/hookpump.hpp` and the corrected §6 of the threading spec.

## A measurement error that cost several rounds

Between the fix landing and it being confirmed, five separate runs reported
**zero** `key` events from a core that was in fact working correctly. The cause
was the capture tool, not the product: `watch.ps1` (a `StreamReader.Peek()` loop
under Windows PowerShell 5.1) received the `hello` line and then went deaf while
the process stayed alive, so it looked like a healthy observer reporting a real
negative.

It was caught by triggering `mode`/`modifiers`/`focus` broadcasts from a second
connection and observing that a *foreground* client received them while the
background capture — still running — recorded nothing. A Python client validated
against the same known broadcasts captured all of them.

Two conclusions were drawn from the bad instrument and are **withdrawn**:

- "The bug is inside `HookInput`, not the pump" — wrong; it came from the broken
  watcher reading 0 while the observers read 384.
- "The `PeekMessage`+`Sleep` observer undercounts" — disproved by direct test:
  `get=384` and `peek=384`, identical over the same keystrokes.

Lesson recorded in the matrix: **validate an instrument against a known-positive
signal before trusting a negative from it.**

## Deterministic comparison (item 6)

Measured with a self-triggering harness — the operator arms and stops the count
from the keyboard with `F12`, so no window alignment with anyone else is needed.
The harness's state machine is self-tested against a canned stream (pre-arm noise
ignored, trigger excluded, stray keys segregated).

### Part 1 — ten discrete taps of `A`

| Measure | Predicted | Observed |
|---|---|---|
| KeyGnosys `KeyA` events | 20 | **20** — 10 `down`, 10 `up` |
| suppressed split | 10 / 10 | **10 true / 10 false** |
| stray keys inside the window | 0 | **0** |
| Independent hook, injected | 10 | **10** |

The suppressed split is the grace-expiry path, not a defect: at ~1.2 s per tap
each hold exceeded the 50 ms window, so each **down** was buffered and suppressed,
the timer expired and forwarded it synthetically — which is the observer's 10
injected events — and each **up** then passed through natively.

**Duplicate physical callbacks are ruled out.** 10 taps produced exactly 20
events, not 40.

### Part 2 — one three-second hold of `A`

| Measure | Observed |
|---|---|
| `down` | **1** |
| `repeat` | **55** |
| `up` | **1** |
| suppressed | 1 true, 56 false |

55 repeats over 4.28 s ≈ 12.9/s, matching the system repeat rate. Autorepeat
stays on the native passthrough path, which is the property that makes the
physical-bitmap `Repeat` derivation load-bearing.

### The 529-vs-1497 discrepancy — resolved

Window misalignment, not duplication. The 529 came from the observer's own 90 s
window; the 1497 from a KeyGnosys counter delta spanning a longer, unsynchronised
period, with injected events filtered on one side only. The two were never
like-for-like. When both are aligned by construction — as above — they agree
exactly, and the independent hook's 32 non-injected events are fully accounted
for by keys pressed outside the trigger window that our count correctly excluded.

# 2026-09-02 — row 9.1 investigation: hook loss NOT reproduced

Investigated before implementing recovery, on the principle that a watchdog for
an undemonstrated failure mode is speculation with a retry loop attached.

## Documented Windows semantics

`LowLevelKeyboardProc` Remarks (learn.microsoft.com, retrieved 2026-09-02):

> "The hook procedure should process a message in less time than the data entry
> specified in the **LowLevelHooksTimeout** value in the following registry key:
> `HKEY_CURRENT_USER\Control Panel\Desktop`. The value is in milliseconds. If the
> hook procedure times out, the system passes the message to the next hook.
> However, on Windows 7 and later, the hook is silently removed without being
> called. **There is no way for the application to know whether the hook is
> removed.**"

> "**Windows 10 version 1709 and later** The maximum timeout value the system
> allows is 1000 milliseconds (1 second). The system will default to using a 1000
> millisecond timeout if the **LowLevelHooksTimeout** value is set to a value
> larger than 1000."

`UnhookWindowsHookEx` documents only nonzero/zero plus `GetLastError`; it says
nothing about a handle the system has already removed, and it is destructive, so
it cannot serve as a health probe.

**Therefore Microsoft states plainly that no affirmative detection API exists.**
Any detection must come from observing delivery, not from asking Windows.

## Reproduction procedure

Scratch experiment (`hookloss.cpp`, never committed — it deliberately blocks
inside a hook callback, the one thing production code must not do).

Two hooks, two threads, one process:

- **victim** — overruns the timeout once, deliberately, via `Sleep()` in its callback
- **control** — never blocks, own thread, own `GetMessageW` pump

The control exists so "no callbacks" can never be confused with "the operator
stopped typing". Both counters are read at the same instant in the same process,
so the windows are aligned by construction. An `F12` start gate on the control
hook lets the operator begin when ready.

Machine: Windows 11 Home 10.0.26200. `LowLevelHooksTimeout = 5000` (explicitly
set in `HKCU\Control Panel\Desktop`).

## Results

| Run | Overrun | victim after | control after | `UnhookWindowsHookEx` | Verdict |
|---|---|---|---|---|---|
| 1 | 2500 ms | **+680** | +680 | returned 1, err=0 | survived |
| 2 | 6500 ms | **+606** | +606 | returned 1, err=0 | survived |

6500 ms exceeds both the documented 1000 ms cap and the machine's configured
5000 ms. In both runs the victim and control counts are **identical**, so every
event that reached the control also reached the victim: the victim was never
removed. The successful unhook with `GetLastError=0` independently confirms the
handle was still live.

**Silent removal did not occur on this build under a single overrun.** The
documented 1000 ms cap also appears not to be in force, since a 2500 ms overrun
did not trip a supposedly 1000 ms ceiling.

## Consequences

**No watchdog, sentinel, or recovery state machine was implemented.** Building
one now would mean designing detection for behaviour we cannot demonstrate,
against an API Microsoft says cannot report it.

**A retraction.** The earlier suggestion that the 2.5-hour-old core had a
silently removed hook is **withdrawn as unsupported**. It was offered as
plausible and never confirmed; the demonstrated cause of that episode was the
deaf `watch.ps1` capture client, and hook removal has now failed to reproduce
deliberately.

**The code defect is nevertheless real, and is narrower than first stated.**
`installed_` is cleared only by our own `uninstall()`. The reinstall branch in
`run()` is therefore reachable *only* for an install that never succeeded — not
for a hook removed after succeeding. Its comment claims otherwise, and
`hookLosses_` can only count the former, so the `input.hook_lost` diagnostic in
SPEC §11 is unreachable in practice. That is a truthfulness problem (P6), not a
missing watchdog.

## Row 9.1 status

Row 9.1 accepts either branch: "Either the hook survives, or it is removed and
re-installed automatically with an `input.hook_lost` diagnostic."

On this machine the hook **survives**, which satisfies the first branch. The
second branch is not implementable without a detection mechanism the platform
does not provide. Recommend rewriting the row to state what is actually
guaranteed, rather than leaving an alternative that cannot be delivered.

Not yet run as a formal matrix row: it needs the load conditions in its own
procedure, not this synthetic overrun.

Three analysis errors were made before section 3 produced usable data, none of
them product defects:

1. A solo-J grace replay was counted as a 3.2 leak. It is row 3.1 working.

### `grace_ms` recommendation

**Keep 50 ms.** The operator's natural chord puts CapsLock 0–16 ms *ahead* of the
bound key, an ordering that never touches the grace window. Narrowing it would
buy ~28 ms of latency the operator cannot perceive, at the cost of margin for the
J-first ordering — which ~15 natural attempts failed to produce even once. That
is the trade SPEC §15.10 exists to prevent. Doing this properly needs the M5
calibration UI and 20–30 samples, not hand analysis.

### Finding D-2 — `button.double_click` misses, and the SPEC is why

**Symptom.** Double-click frequently registers as two single clicks ("no click"),
and sometimes as a triple.

**Cause.** `Core::scheduleDoubleClick` emits the first pair immediately and
schedules the second at `now + doubleClickInterval()`, where the Windows backend
returns `GetDoubleClickTime()` — **410 ms on this machine, 500 ms by default**.

`GetDoubleClickTime()` is the *maximum* gap the OS will accept as a double-click,
not the gap to use. Scheduling at exactly that value lands on the threshold, and
`serviceDoubleClicks()` runs on the 60 Hz core loop, so the delivered gap is
`interval + 0…16.7 ms` — **over the limit**. Windows then sees two independent
single clicks.

The triple follows: an attempt that appears to do nothing invites a second press,
and two delayed second-clicks then land around the new first click.

**The code faithfully implements a SPEC sentence that is wrong.** §7.2 says the
pairs are *"separated by the OS double-click interval"* — it should be **within**
it — and asserts *"the interval is tens of milliseconds"*, which is off by an
order of magnitude.

**Ruled out.** Autorepeat is not a contributor: `layer_engine.cpp:269` suppresses
a repeated press of a key already driving an action, so a held `X` cannot queue
extra clicks.

**Proposed fix, not applied.** Schedule the second pair at a fraction of the
interval — `interval / 4`, or a small fixed delay around 60 ms — and correct both
§7.2 sentences. Needs a test asserting the scheduled gap is strictly less than
the backend's reported interval, which would have caught this.

### D-2 resolved — 2026-09-04

Fixed in `7424c35`. `doubleClickDelay()` now waits `min(interval / 4, 80 ms)`,

SPEC §7.2 corrected on both counts.

### Finding M-1 — row 7.2 expects behaviour the SPEC does not require (matrix defect)

Row 7.2 expects "The remaining windows keep their indices. **The freed slot is
empty.**"

the property the row exists to protect — but slot 5 was immediately backfilled

This is the implementation behaving sensibly, not a defect. `slots.cpp:19-21`
assigns any window "not currently in a slot" to the lowest free index; it does
not distinguish a newly-opened window from an existing overflow one. SPEC §6.5

on what happens to an overflow window when a slot frees. The alternative —
leaving the slot dead — would strand overflow windows as permanently

index the user has learned (the window that owned it is gone).

Severity: the row asserts something stricter than either the SPEC or the design
intends, so it cannot pass whenever more than nine windows are open.

should read "a window with no slot takes the lowest free index", and row 7.2
should expect the freed slot to be empty *only when no overflow window exists*.
Not fixed here: changing slot semantics is a design decision, and this milestone
has twice found that the right move is to correct the specification rather than
bend the code to a row.

# 2026-09-15 — O-1 measured: presses the engine never observed

**Working diagnosis:** "the engine did not observe the press" does not imply
"Windows did not receive the press". SPEC §6.3.4 suppresses "a release for a
key with no matching press" and forbids forwarding a release whose press was
not forwarded; both assume the engine observed every press.

**Repaired production core** (`build/default`, O-3 branch). Captures in the
git-ignored `captures/o1/`. Instruments per run: an independent key observer
installed **before** the core (called after the core's hook, so it sees only
what the core passes on), one installed **after** the core (sees physical events
before the core can suppress them), the core event recorder, and
`delayed.ps1` samples of Windows' `VK_LSHIFT` state. The pre-core observer was
validated with 3 physical `Q` presses and a Left Shift press whose auto-repeat
it recorded (first repeat 500 ms after the press, then ≈ 30 ms — the machine's
keyboard delay/rate settings).

**Code facts that shaped the predictions.** The hook classifies a key-down for a
key it already holds as down as a *repeat* (`physical.cpp`), otherwise as a
*down*. The engine suppresses a *repeat* for a key it has not forwarded
(`layer_engine.cpp:371-379`). While disabled, keys pass natively without the
engine, the hook's physical bitmap keeps tracking, and `SetEnabled` runs
`engine_.releaseAll`.

## M1 — P1: Left Shift held across core start — not stuck

`delayed.ps1 -Do start-core`: core answering 141 ms after FIRE; evidence armed
and release prompt at +947 ms. Windows: Shift down from −4720 ms, **up at
+1391 ms**, up through +8946 ms. Pre-core observer: auto-repeats continuous across
the install and the release — the core passed every Shift event. Core stream:
`repeat, suppressed: false` … `up, suppressed: false`.

## O-1 live regression, Group A (rows 1.1, 1.3) — **FAIL**

Branch `investigate/m3-o1-unobserved-press`, HEAD 8c72315, core pid 36196 alone in
a conhost window, layer off (normal / hybrid / enabled). Instruments: one hook
observer installed *after* the core (`groupA/keys-post.csv` — physical ground
truth, `probe: ok`), two installed before it (`o1/m2r-keys-pre.csv`,
`o1/m2r-keys-post.csv` — what reached Windows), and the core recorder
(`groupA/core.jsonl`, known-positive mode lines). Operator typed `Q`x3, "the quick
brown fox jumps over the lazy dog", then Shift+`abc` and `abc`.

**Instrument defect found first.** `observe_keys.ps1:30` stamps with
`Stopwatch.StartNew()` — elapsed since *that process* started — and `record.py`
stamps relative to recorder start. These are not the system-wide QPC clock that
`delayed.ps1` samples with, so capture files from different processes cannot be
aligned by raw timestamp. The offsets here were recovered by delta-matching
(+14235951.2 ms and +14082756.9 ms); both downstream observers then agreed with
each other event-for-event. Any earlier cross-process claim resting on raw
timestamps from these two instruments needs re-checking.

**What the core did.** 385 physical-stream events; 56 physical events withheld
(53 downs, 3 ups) and 56 injected events emitted — matching the core's own
`suppressed` counts exactly. No downstream event lacked a ground-truth match: the
core invented nothing and duplicated nothing. The three withheld *releases* (`N`,
`H`, `Y`) were each answered by an injected release 4–15 ms later. No release was
withheld without provenance — **the O-1 defect itself did not recur.**

**A different P7 violation.** Each tap is delivered as: physical down withheld,
injected down at grace resolution, physical up forwarded. For five of 77 taps the
two arrived at Windows in the wrong order — the forwarded physical **up first**,
the injected **down second**, leaving Windows holding a key with no release to
come:

| Key | physical up | injected down | separation | stuck after? |
|---|---|---|---|---|
| `B` | 359959 | 359963 | +4 ms | no |
| `F` | 362055 | 362056 | +1 ms | no |
| `P` | 363751 | 363752 | +1 ms | no |
| `O` | 411719 | 411722 | +3 ms | no |
| `Space` | 413127 | 413142 | **+15 ms** | **yes** |

`Space` was the last of these and is **still held**: `GetAsyncKeyState(0x20) &
0x8000` read true on ten samples over two seconds while the same probe read false
for a never-pressed key and for every other key, modifier and mouse button. The
operator did not notice, and would not: a synthetic down does not autorepeat, so a
stranded `Space` produces no visible character.

**Correction to an earlier draft of this entry.** It claimed the strand persisted
~4 hours with no intervening keyboard activity. That was wrong: the capture had
simply not been re-read. 551 further events arrived later (ordinary typing), the
stuck `Space` was cleared by a subsequent `Space` press supplying the missing
release, and a re-probe found nothing held. Duration of the strand is therefore
**not established** — only that it outlived Group A and every key pressed in it.

Note also that these elapsed clocks cannot be converted to wall time: between the
two reads the capture clock advanced ~10 min while wall time advanced ~4 h, so the
machine was suspended for most of it and `Stopwatch`/QPC did not tick.

**The inversion, over a larger sample.** The later typing contained five more
inversions, giving ten in all:

| separation (physical up → injected down) | count | stranded |
|---|---|---|
| 0–4 ms | 9 | 0 |
| 15 ms | 1 | 1 (`Space`) |

Three of the later inversions (`I`, `O`, `F`) were followed by an injected **up**
as well — the engine emitted a complete replayed tap — while the rest emitted only
the down. The correlation is clean at n=10 and matches the queueing hypothesis:
an injected down emitted from *inside* the hook callback handling the physical up
is queued ahead of it, so the observer's ordering is not Windows' delivery
ordering, and only a replay arriving later (from the grace timer thread, after the
callback returned) actually inverts at Windows. Still a hypothesis — it predicts
the outcome of all ten cases but has not been tested directly.

The pre-core observer `o1/m2r-keys-pre.csv` and the second downstream observer
both exited normally (code 0); the first covered Group A in full, ending on the
`Enter` that closed it. Both must be restarted before any further live row.

Why the four 1–4 ms inversions did not strand and the 15 ms one did is **not
established**. A plausible reading — the short ones are emitted from inside the
hook callback and so are queued ahead of the physical up despite being observed
after it, while the 15 ms one came from the grace timer thread after the callback
returned — fits all five cases but has not been tested. Recorded as a hypothesis,
not a finding.

This is separate from O-1 (a routing-provenance defect) and from O-2/O-3/O-4. It
is a race between the grace timer and the hook callback. No fix attempted.
`panic.ps1` would not have cleared it: it releases modifiers and mouse buttons
only, not ordinary keys.

### Finding O-5 — cross-channel delivery ordering can violate P7

Confirmed transport/order defect, distinct from O-1 and O-2. Surfaced by the
Group A FAIL above. **No live experiment was run:** the code-path analysis settled
the mechanism and contradicted the working hypothesis, so it was reported first.

**Rejected hypothesis, preserved for the record.** The working hypothesis was that
the replayed synthetic Down is emitted *synchronously, from inside the
`WH_KEYBOARD_LL` callback for the physical Up*, and that Windows therefore queues
it ahead of that Up. **This is false: no such code path exists.** Every synthetic
event is emitted asynchronously by the core loop thread draining the work ring.
The prediction structure (earlier emission ⇒ safe, later ⇒ strand) survives, but
the boundary is not "callback return" and the emitter is not the callback thread.
The repair design follows from the real mechanism, below.

**The replay is never emitted inside the hook callback.** There is no such code
path. `hook_input.cpp:244` calls `translateDecisions`, which pushes
`WorkItem::SendKey` onto the work ring (`hookchannel.cpp:86`); the **core loop
thread** drains that ring and calls `sendKey` → `SendInput` (`core.cpp:349-353`).
Every synthetic event is therefore emitted asynchronously, on a different thread,
at an unbounded delay after the decision.

A forwarded *physical* event takes a different route entirely: `translateDecisions`
returns `native = true` for a single `Forward` decision matching the event in hand
(`hookchannel.cpp:76-81`), and the hook callback then returns `CallNextHookEx`
(`hook_input.cpp:257`), delivering it **synchronously** down the hook chain.

So two channels carry ordered obligations with no ordering between them:

| channel | carries | latency |
|---|---|---|
| work ring → core thread → `SendInput` | every synthetic (replayed) event | async, unbounded |
| `CallNextHookEx` from the hook callback | every natively forwarded physical event | synchronous |

**The defect.** `layer_engine.cpp:335-341`: a release for a key already marked
`kForwarded` emits exactly one `Forward(code, Up)` decision — which is precisely
the shape `translateDecisions` sends down the *native* path. When the grace expiry
replayed that key's press (`tick` → `Forward(code, Down)`) but the core thread has
not yet drained and injected it, the release overtakes the press. Windows receives
**Up, then Down**, and holds the key.

The `hookchannel.cpp:59-64` comment states the intended rule — "anything more than
one decision means something has to be ordered around it … the physical event must
be suppressed and re-synthesised so the order is ours to control." The rule is
applied per *decision batch*. It does not account for work already queued from an
**earlier** batch, which is exactly the grace-expiry case.

**The ten observed inversions split cleanly by branch**, confirmed against the
downstream capture:

| branch | n | physical Up reached Windows | synthetic Up | genuinely inverted |
|---|---|---|---|---|
| `takePending` (`layer_engine.cpp:343-355`) — fast tap resolved at the Up | 3 | **no** (suppressed) | yes | no — observer artifact only |
| `kForwarded` (`layer_engine.cpp:337-341`) — grace already expired | 7 | yes | no | yes, 1 stranded |

The three `takePending` cases emit two decisions, so both events go through the
ring in order and the physical Up is suppressed — never inverted at Windows at
all. They *appear* inverted only because the ground-truth observer sits upstream
of the core's hook and records a physical Up that the core then suppresses.
**Observer ordering is not delivery ordering, and upstream observation is not
delivery at all.**

Of the seven `kForwarded` cases, six won the race (the core thread injected before
the forwarded Up completed the hook chain) and one — `Space`, the +15 ms case —
lost it and stranded.

**Answers this establishes without further measurement.** Why 0–4 ms is safe: in
three cases nothing was inverted at all, and in the rest the injection beat the
Up's chain traversal. Why the delayed case strands: the Up was delivered before
the queued Down. Why later typing self-clears: the next tap of that key emits its
own Down and Up, and that Up discharges the stale Down. Whether deterministic: the
*defect* is deterministic — a native fast path that ignores queued work — while
*which* occurrence strands is a genuine thread-scheduling race inside it.

**Still to measure.** Whether injection preceded delivery of the forwarded Up, per
sample. This needs in-process timestamps (hook callback entry and return for the
Up, and immediately before `SendInput`) on one QPC clock — the existing
instruments cannot see either boundary. The experiment must vary *core-thread
scheduling delay*, not "replay timing around the callback boundary": that boundary
does not exist as designed.

**Relationship to O-2.** Same grace/replay machinery (`pending_`, `tick`,
`kForwarded`, the work ring), different property. O-2 is ordering *among buffered
presses inside the engine* — the engine emits the right events in the wrong order.
O-5 is ordering *between the engine's output channel and the native passthrough* —
the engine emits correct decisions and the transport inverts them. An O-2 fix
inside `LayerEngine` would not touch O-5, and vice versa. Keep separate.

**Smallest plausible repair boundary.** `translateDecisions` may only take the
native path when nothing is pending for that key in the work ring — or, more
simply, when the ring is empty. Otherwise suppress and re-synthesise, which is
what the existing comment already says the rule is. That is one condition in one
function; it changes no engine semantics and no SPEC rule. **Not implemented.**

#### O-5 repair — implemented, automated verification only

Design: `docs/superpowers/specs/2026-09-16-o5-transport-order-design.md`. Not yet
live-validated; Group B still parked.

**The rule implemented.** Once the Windows-visible Down for a physical press is
committed to native or synthetic delivery, the remainder of that physical press
stays on that delivery channel. `Synthetic` is a *routing commitment*, not a
receipt: hook routing never depends on whether `SendInput` later succeeded, which
is what keeps the proof single-threaded.

`DeliveryChannel` (new, `core/include/kgn/delivery_channel.hpp`) holds one value
per key — `None` / `Native` / `Synthetic` — written and read only on the hook
thread. `translateDecisions` gains one condition: the native fast path also
requires `channel->nativeAllowed(code)`. Commitments are made where the channel
is chosen, per *decision* rather than per event in hand, because a grace expiry
carries no physical event and one physical event can resolve several keys.

**Kept separate from `DeliveryProvenance`.** They answer different questions about
different halves of the path and are consulted on disjoint paths: provenance
decides *whether the engine is consulted at all* (`hook_input.cpp:211`, before the
enabled check), and its `Native` route returns at 223-229 without ever reaching
`translateDecisions`. So a delivery commitment can never block an O-1 native
forward, and O-1's mirror obligation is untouched. Folding them into one enum
would have needed the cross product — an ordinary bound key is Engine-routed and
Native-delivered; a grace replay is Engine-routed and Synthetic-delivered.

**Deterministic reproduction.** `test_delivery_channel.cpp`, 16 tests, no thread
and no sleep. The canonical one publishes `Forward(K, Down)`, leaves it undrained,
then translates `Forward(K, Up)` for the same press and asserts the native bypass
is refused and the drained order is Down → Up. Against the pre-repair code it
fails, with 6 others.

| mutation | tests failed | caught by |
|---|---|---|
| guard removed (pre-repair code) | 7 | the canonical regression, first |
| commitment cleared at the press, not the release | 9 | canonical + `the_commitment_outlives_…` |
| guard inverted | 14 | almost everything |
| global instead of per-key | 2 | `an_unrelated_key_is_not_blocked_by_a_committed_one` |

**Capacity.** A repeat of a synthetically committed press now emits one work item
where the native path emitted none. The proof in `hookchannel.hpp` is unchanged
and the reasoning is recorded there: the admission gate already counts a Repeat as
obligation-creating, a repeat does not change `U`, and a stalled core loop makes
the stream self-limiting — repeats are refused and suppressed below the gate,
which strands nothing because the key is already down and its release still comes.

**SPEC.** No normative change. §6.3.3 governs the order the *engine emits*
decisions in, and the engine was correct here; the transport reversed them. The
P7 text at §6.3.2 was met to the letter — the release *was* forwarded — while the
key was left held, so a non-normative note was added there against the sentence
that assumes a single delivery path.

**Verification.** Windows RelWithDebInfo 19/19; Windows Debug with `KGN_WERROR=ON`
19/19, no warnings; Linux g++ 13.3 `-Werror` 15/15, no warnings; pytest 90 passed;
`git diff --check` clean.

**Instrument note.** `test_core` segfaults under the Bash tool's default PATH
because the `-O2` binary loads Git-for-Windows' `libstdc++-6.dll` instead of the
msys64 UCRT64 one it was built against. It is not a defect and not related to this
change — it reproduces at HEAD with the repair stashed, and passes 29/29 once
`/c/msys64/ucrt64/bin` leads the PATH. Every result above was taken with that PATH.

#### Row 1.3 — Shift held while typing letters

**New observation, unrelated to O-5: `ShiftRight` is invisible to the engine on

distinct codes, LShift among them, RShift absent. `scancode_keymap.cpp:52` does

channel commitment), but it means the engine cannot see right Shift at all, which
would matter to the Shift+CapsLock escape gesture and to modifier publication.
